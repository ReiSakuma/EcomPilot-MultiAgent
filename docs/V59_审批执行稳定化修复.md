# V59 审批执行稳定化修复

## 修复目标

本次修复解决用户确认方案后出现的三段式故障：浏览器执行票据不匹配、后端无法序列化 `needs_attention`、前端把非 JSON 的 500 响应当作 JSON 解析。

## 核心改动

1. 浏览器票据在服务端保存完整的已审批 `ExecutionPlan`。Seller Center 页面只回传可编辑业务字段，服务端核对这些字段未被篡改后，执行服务端保存的完整计划。任务 ID、运行 ID、检查点版本、Artifact 哈希和 payload 哈希不再通过 DOM 表单往返。
2. 内部 `needs_attention` 对用户 API 映射为 `technical_failed`，但保留失败协议和技术证据。系统不会把“写入结果未知”伪装成成功，也不会自动重复写入。
3. 用户端所有关键请求先读取文本，再尝试解析 JSON。即使服务返回非 JSON 错误页，也只展示可读错误，不再出现 `JSON.parse: unexpected character`。
4. 运维端拆分“本次运行模型调用”和“任务累计模型调用”。审批恢复运行通常显示 `0 / 9`：前者表示审批阶段没有重复调用模型，后者表示生成整个方案累计调用 9 次。
5. pytest 默认把 checkpoint、trace、conversation、runtime queue、idempotency、browser artifact 和 security ledger 写入独立临时目录，不再污染真实演示数据。

## 安全边界

- 页面修改价格、库存、优惠、标题等任一已审批业务字段时，票据仍会拒绝执行。
- 页面不能覆盖服务端保存的租户、任务、运行、检查点和 Artifact 溯源信息。
- 票据保持一次性、短时有效和用途隔离。
- 执行状态不确定时停止自动重试，等待核对，避免重复上架或重复创建优惠。

## 验证结果

- 完整离线回归：`540 passed`。
- 新增 HTTP 接口测试覆盖 Seller Center 页面仅提交可见字段的真实协议路径。
- 完整回归运行后，真实 `data/checkpoints` 没有产生测试任务。
