# EcomPilot v39 混沌测试与生产就绪验收

## 1. 版本定位

版本号是 `0.39.0`，发布标识是 `v39-chaos-readiness`。这是既定技术路线的最后一个版本，也是面试演示的功能冻结参考实现。

“参考实现验收通过”只说明项目代码在本机可重复证明核心行为，不等于生产认证。真实生产仍需企业身份、云数据库、共享消息队列、跨实例熔断、容器隔离、真实电商平台和持续值班体系。

## 2. 六类故障演练

`app/operations/chaos.py` 在明确注入点运行确定性实验：

1. 网络分区：读取工具连续失败两次，持久任务在第三次租约内恢复。
2. 数据库切换：Repository 调用失败一次，事务状态保留并由新尝试完成。
3. 重复投递：24 个并发重复事件以租户级幂等键收敛成一个 Job。
4. 模型限流：模拟两次 429，在重试预算内恢复。
5. 慢工具：非关键证据超时后明确降级，不伪装为完整成功。
6. 摘要污染：篡改后的事实快照因来源版本与 SHA-256 不匹配被拒绝，且摘要永远没有写权限。

这些实验使用真实的本地协议代码，但网络分区和数据库切换是协议边界模拟，不是云机房断网或真实主从数据库切换。

## 3. 五种终态

内部 Workflow 可以有很多运行状态，对外统一投影为：

- `success`：必要步骤与验证完成。
- `waiting_user`：等待补充关键字段或确认高风险写操作。
- `business_rejected`：价格、库存、权限或合规规则明确拒绝。
- `degraded_completed`：主任务完成，但某个可选证据不可用并被明确标注。
- `manual_attention`：自动恢复预算耗尽，进入人工处理。

`app/operations/terminal.py` 是唯一投影入口。它阻止技术异常无限扩散为新状态，也防止“失败但 UI 显示成功”。

## 4. 指标、容量与 SLO

`runtime_metric_events` 持久记录排队、执行耗时、任务重试、死信、幂等重放和业务效果。容量验收并发提交与消费 240 个任务，报告 P50/P95、吞吐、重复任务和死信数量。

当前参考 SLO：

- 六类混沌场景恢复率不低于 99%。
- 本机入队 P95 不高于 2 秒。
- 本机任务消费吞吐不低于 5 Job/s。
- 重复任务数为 0。
- 跨租户泄漏数为 0。

安全指标违反时触发 `page` 级告警；性能基线违反时触发 `ticket`。这些阈值是面试参考环境的初始值，生产部署必须按真实流量重新校准。

## 5. 租户隔离审计

审计验证两个租户使用相同幂等键和同名商品资源仍产生独立记录，且一个租户不能通过 Job ID 读取另一个租户任务。业务效果和状态快照也按租户过滤。

## 6. 运维与证据

运维后台新增只读 `Resilience` 页，不提供创建、审批或执行按钮。Run Bundle 2.4 增加：

- 当前任务的五类终态投影。
- 六类混沌实验及尝试次数。
- 容量报告和 Worker 建议。
- SLO 指标与告警。
- 租户隔离审计。
- SQLite 队列指标、重试、恢复、幂等、锁、上下文防污染与补偿证据。

## 8. 最终边界

v39 之后不再以增加面试概念为目的继续迭代。真实落地应作为集成工程处理：SQLite 协议迁移 PostgreSQL/Redis/消息队列、身份迁移 OIDC、沙盒迁移容器或微虚拟机、Seller Center 接真实平台测试账户，并在目标环境重新进行压力与灾备演练。

## 9. 用户工作台布局修正

历史会话条目使用固定边界、横向裁剪和省略号，长标题与摘要不会进入对话区域。桌面和平板端从历史会话标题栏收起或重新展开历史栏，释放的宽度只交给对话区，右侧结果区保持固定；状态保存在浏览器本地。移动端仍使用独立抽屉。业务结果页签使用固定高度和字体基线补偿，文字到上下边框的视觉距离一致。浏览器验收脚本检查边界、宽度分配、折叠持久化、重新展开、桌面/移动端横向溢出和控制台错误。

## 10. 前置准入与安全返工

创建商品的外层路径现在是：

`receive -> compile_request -> preflight_gate -> listing_workflow -> answer`

`preflight_gate` 在任何专业 Agent 和业务工具之前检查：

- 商品类别、成本、售价和库存是否完整且来自用户明确输入。
- 同一请求是否给出互相冲突的关键数值。
- 成本、售价和最低毛利率在不做促销时是否已经数学可行。
- 用户是否要求把未确认功能、产品形态、量化性能或禁止性营销词写入宣传。
- 是否存在覆盖系统规则、绕过审批、索取隐藏指令或密钥的提示注入。

未通过时不创建 `TaskState`，也不运行 Market、Listing、Strategy、Review 或 Browser Agent。响应优先说明被拒绝的宣传或安全原因，再列出仍缺少的真实业务字段。信息完整但包含未确认宣传时，用户必须明确确认“去除这些宣传并继续”。

准入采用两段式编译。第一段是零模型调用的确定性快速检查：明显缺少必填字段、毛利不可行、关键数值冲突、已知虚假宣传、提示注入或越权请求会直接进入澄清或拒绝，不消耗模型 Token。只有第一段通过后，真实 LLM Request Compiler 才补充识别更自然的未确认宣传候选；候选必须能在用户原文中找到才会被采纳。规则层始终是不可绕过的最终裁决者，因此该设计既保留模型的语义识别能力，也不把安全边界交给概率模型。

审核返工使用独立 `strategy.revise` 能力，只允许 `calculate_margin` 和 `check_inventory` 两个低风险确定性工具。可信数字会强制覆盖模型文案中的错误金额、到手价和毛利率，因此修订权限、工具调用和语义审计使用同一协议。

## 11. 会话续接、空证据与输入错误收敛

待澄清请求不再自动绑定下一条用户消息。只有明确补充缺失字段、修正被指出的字段或回复“去除这些宣传并继续”时才续接；新的“上架、上新、发布、创建”命令会建立新请求，旧价格、库存和宣传事实不会被继承。

市场研究使用规范类目查询，“游戏耳机、蓝牙耳机、头戴式耳机”映射到“无线耳机”市场样本。规范化后仍无样本时，Market Agent 返回 `evidence_status=degraded` 和低置信度证据，后续 Agent 只能使用用户确认事实，不能伪造价格区间，但工作流不会因为空数据被误判为技术失败。

成本、售价、库存和毛利率先经过业务范围检查，再构造 Pydantic 请求模型。负成本、非正售价、负库存及超出 `[0%, 100%)` 的最低毛利率统一转换为中文 `invalid_field_value` 澄清响应。API 与事件流还保留防御性错误脱敏，内部 Schema 类型和文档链接不会暴露到用户页面。
