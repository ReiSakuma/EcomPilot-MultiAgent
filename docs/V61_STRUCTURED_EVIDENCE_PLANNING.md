# V61 结构化证据规划

## 1. 版本目标

v61 解决的核心问题是：Strategy Agent 可以自主选择证据工具，但不能因为一次选择过多工具、工具参数错误或某个可选工具失败，就造成调用膨胀、输出截断或整个商品上新失败。

本版把“模型思考需要哪些证据”和“系统真正执行哪些工具”拆成两个明确阶段：

```text
可信任务状态
  -> 模型返回 EvidencePlan（0 至 2 个工具）
  -> Pydantic 校验数量、名称和唯一性
  -> 框架注入可信参数并逐个执行
  -> 生成紧凑 EvidenceLedger
  -> 模型基于 Ledger 生成候选策略
  -> 确定性工具计算毛利、库存并过滤候选
```

## 2. 修改前后对比

修改前，候选方案模型可以在一次 ReAct 循环里持续选择工具。即使系统设有工具上限，限制也发生在模型已经生成调用之后；重选、拒绝和长工具结果会继续占用上下文，容易形成“超限后重试、重试后更长”的连锁反应。

修改后，模型第一次只提交结构化计划，不直接执行工具。计划通过 Schema 后，框架最多执行两个工具。候选方案模型只读取执行后形成的短 Ledger，并且该阶段不开放工具调用。因此，工具数量在执行前就已经收敛。

## 3. 核心协议

### EvidencePlan

`EvidencePlan` 表示模型希望补充的可选证据：

- `selected_tools`：最多两个、不重复，只能来自允许列表；
- `decision_question`：说明调用该工具要解决什么决策问题；
- `skip_reason`：不需要可选工具时说明原因。

允许的工具为需求预测、历史活动查询和竞品价格趋势分析。模型拥有“选哪个”的自主权，但没有“执行任意工具”的权限。

### EvidenceLedger

`EvidenceLedger` 是工具结果的决策级短摘要，而不是原始返回值的复制：

- 工具执行状态；
- 对策略有用的结论；
- 少量受限事实；
- 置信度、来源类型和引用；
- 是否发生受控降级及其原因。

原始工具结果仍保存在任务结果和 Trace 中用于审计，但不会被重复注入候选生成 Prompt。

## 4. 参数与权限边界

模型只能选择工具和提出决策问题。真正的工具参数由框架从已校验任务状态生成：

- 品类来自已确认商品品类；
- 售价来自当前可信方案；
- 目标人群来自任务约束；
- 查询天数和返回数量由系统限定。

这样可以避免模型把 199 元改成 19.9 元、扩大查询范围、跨租户读取数据，或者通过参数绕过工具权限。

## 5. 失败与降级

可选证据不是商品上新的硬门禁：

1. 计划第一次不合法时，允许一次受控 JSON 修复并再次执行 Pydantic 校验。
2. 计划仍不合法时，记录 `evidence_plan_degraded`，按零个可选工具继续。
3. 某个工具失败时，只把该项记为 `failed`，其他成功证据继续使用。
4. 工具异常原文保留在 Trace，不直接进入候选 Prompt，避免错误文本污染模型。

基础售价、成本、库存、毛利和合规检查仍是硬门禁，不会因为“可选证据可降级”而被跳过。

## 6. Artifact 与 Run Bundle

`StrategyArtifact` 新增 `evidence_plan` 和 `evidence_ledger`。导出的 Run Bundle 检查：

- 计划工具是否不超过两个；
- 工具名称是否唯一；
- Ledger 是否处于 `completed`、`repaired` 或 `degraded` 合法状态。

这使面试演示可以回答四个问题：模型想查什么、系统最终允许查什么、工具得到了什么、失败时为什么继续或降级。

## 7. 测试覆盖

专项测试覆盖：

- 三工具计划和重复工具计划被 Schema 拒绝；
- 三工具输出在执行前受控修复为两个；
- 候选生成阶段无法追加模型工具调用；
- 计划修复失败后按零工具继续；
- 单个工具失败不丢弃另一个成功结果；

## 8. 当前边界

v61 只治理 Strategy 候选生成前的可选证据规划。它没有通过简单提高输出长度掩盖截断，也没有删除工具数量上限。ReAct 每轮上下文滚动压缩、候选选择失败后的确定性强制收尾，以及真实 DeepSeek P95 压测分别留给 v62、v63 和 v64。

在启用动态候选时，Strategy 正常路径通常包含证据规划、候选生成和候选选择三次模型调用；非法 JSON 可能触发受控修复。因此真实模型测试建议将 `ECOMPILOT_LLM_MAX_CALLS_PER_AGENT` 设为 7，而不是把该值理解为每次任务都必须调用七次。
